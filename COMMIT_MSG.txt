MusicPlayer: swap mpv subprocess for in-process miniaudio streaming

Playing a track no longer spawns mpv (~24MB private RSS, the OOM
killer's first pick on the 64MB targets). The new _MiniaudioPlayer
streams the file chunk-by-chunk through python-miniaudio into one
ALSA device -- kilobytes of buffer, no spawn latency, and a single
ALSA client (same reasoning as Koki's mixer).

- pause/resume = device stop/start with the same stream generator
  (it keeps its position), replacing SIGSTOP/SIGCONT on mpv
- progress bar shows the real decoded-frame position; the wall-clock
  estimate remains only for the mpv fallback
- end-of-track via stream_with_callbacks end_callback
- stream decode buffer sized to the device period (default 500ms,
  NEODCT_MUSIC_ABUF_MS overrides): miniaudio raises mid-callback if
  the device asks for more frames than frames_to_read allocated --
  found by the headless test; the track would hang silent forever
- mpv kept as automatic fallback when miniaudio is missing or its
  device fails to init; a bad file (DecodeError) does NOT demote the
  session to mpv. NEODCT_MUSIC_AUDIO=subprocess|miniaudio forces a
  backend (same convention as NEODCT_KOKI_AUDIO)
- flac/ogg now scanned + playable; aac only via the mpv fallback
  (miniaudio has no aac decoder)
- wav/flac/ogg durations via miniaudio.get_file_info (mutagen only
  handled mp3)
- BR2_PACKAGE_PYTHON_MINIAUDIO=y added to qemu + luckfox defconfigs
  (it lived only in the live .config; a clean rebuild would drop it)

Verified headlessly (NULL backend, real app module, UI stubbed):
play/pause/resume/position, end detection, replay after stop,
bad-file and device-failure fallback paths, plus a real mp3 decode
sweep -- 17 checks + mp3, all green. Also noted in the 0.3.0a
CHANGELOG MusicPlayer section.

INCOMING CALLS: the phone rings, interrupts apps, Answer/decline

Round one of telephony is complete -- NeoDCT now receives calls.

- IncomingCall(BaseException) raised from read_keypress (the chokepoint
  every screen funnels through) unwinds whatever app is running. It
  derives from BaseException exactly like KeyboardInterrupt so an app's
  `except Exception` can't swallow a ringing phone; unwinding still runs
  the apps' finally blocks, so MusicPlayer/Koki release the ALSA device
  before the ringtone starts. launch_app/render_menu re-raise it instead
  of showing the crash screen; the core loop catches it and rings. The
  3310 didn't multitask either -- suspend/resume is post-alpha.
- New System/ui/Dialer/incoming_screen.py, built to the 3310 photo:
  caller name or number across the top (auto-shrunk; a full USA number
  never runs off), flashing "calling" bottom-left, softkey "Answer",
  C declines. Phonebook lookup matches on the last 10 digits so a stored
  "555-1234" resolves a "+1616555..." caller ID. A late +CLIP updates
  the label live; _ring_tick waits one poll cycle for it so the screen
  doesn't open on "Unknown" (withheld numbers still ring after 0.6 s).
  Caller hangs up first -> screen returns "gone" on its own.
- NotifyService gained the ringer: system.audio.ringtone decoded once
  and looped in-process via python-miniaudio (no ~24MB mpv), mpv as
  fallback. Paths with spaces never touch a shell. Resolution chain
  never rings silently: exact path -> same stem with another extension
  (survives the .wma->.mp3 re-encode) -> Nokia Tune/Ring Ring -> any
  playable tone, each step logged.
  NOTE: settings.prop says "Brave Scottland.mp3"; the file is "Brave
  Scotland.mp3" (one t) -- rings the fallback until that's fixed.
- SettingsStorage default ringtone .wma -> .mp3.
- Sim hook fix: /tmp/neodct_sim_ring rings once per write/touch
  (mtime-tracked). It used to re-ring instantly after a decline, making
  the decline path untestable; `rm` while ringing still = caller gave up.
- Ring volume control in Tones is deliberately left for later.

Tested against the real main.py/NotifyService/ModemService code (PIL and
UI stubbed): exception semantics through a greedy app handler + finally,
_ring_tick CLIP grace and withheld-number path, answer/decline/gone
flows asserting ring-stop happens before answer takes ALSA, ringtone
resolution (typo, space, wma->mp3, unset), loop generator wrap, and the
sim ring hook lifecycle.

FULL-DUPLEX CALLS: mic uplink via arecord into the PCM port

The other half of the audio path -- a complete NeoDCT OS phone call.
The SIM7600's CPCMREG stream is bidirectional, so the uplink mirrors
the downlink with pure alsa-utils plumbing:

    speaker <- aplay   <- /dev/ttyUSBn   (far end's voice, existing)
    far end <- /dev/ttyUSBn <- arecord   (USB sound card mic, NEW)

- arecord -q -t raw -f S16_LE -r <pcm_rate> -c 1 -D <dev> <port>,
  spawned next to aplay at dial/answer, killed with it at teardown.
  arecord ships in the image already (alsa-utils APLAY installs both).
- system.hw.modem_mic_device picks the capture device ("default";
  "plughw:N,0" to pin; OFF/NONE for deliberate listen-only).
- Watchdogs split: speaker restarts indefinitely (3 s holdoff), the mic
  gets three attempts then gives up into listen-only with a logged hint
  (`arecord -l`) -- a guest without a capture device is a normal state,
  not something to spin on.
- Real hardware uses an embedded stripped USB sound card = the exact
  same snd-usb-audio path as QEMU passthrough; this plumbing is final.
  If QEMU's usb-audio turns out playback-only (`arecord -l` empty),
  virtio-sound-pci does capture and CONFIG_SND_VIRTIO=y already ships.

Tested with recorded-Popen fakes over a pty PCM port: dual spawn with
correct args, mic three-strikes -> listen-only (then stays quiet),
speaker restart, hangup kills all live pipes, OFF/custom device
settings pass through. py_compile clean.

mic uplink: auto-detect the capture card (QEMU usb-audio is playback-only)

First full-duplex field test confirmed QEMU's usb-audio device exposes
zero capture endpoints (arecord -l empty in the guest) -- the mic pipe
did its 3-strikes give-up as designed. The fix is passing the USB mic
itself through (same snd-usb-audio path as the real phone's embedded
sound card), which creates a second guest sound card... where ALSA's
"default" (card 0 = playback-only QEMU USB Audio) becomes a trap.

- system.hw.modem_mic_device now defaults to AUTO: scan /proc/asound
  for the first cardN with a pcm*c (capture) node -> plughw:N,M.
  Explicit devices still pass through; OFF still means listen-only.
- No capture device found = one clean log line and a listen-only call,
  not three arecord deaths.
- Also confirmed in the field: CPCMREG=1 -> ERROR at dial time on this
  firmware, then OK on the post-connect retry -- the retry path earns
  its keep.

Tested against a fake /proc/asound tree: playback-only card 0 + mic on
card 1 -> plughw:1,0; capture on card 0 (real-hardware shape) ->
plughw:0,0; no capture -> mic pipe skipped; hotplug found on next call.

immutable rootfs + on-device system updates (branch immutable_n_updates)

Read-only squashfs root verified by dm-verity, /NeoDCT/User on its own
partition, and .ndsw update packages installed from an SD card. QEMU-only
so far; the Luckfox NAND/UBI layout is deliberately untouched.

Why an initramfs. You cannot dd over the squashfs the kernel is
demand-paging from, so SystemUpdate never writes the system partition. It
verifies a package, copies the image to the user partition as a pending
update and reboots; a ~1.3MB initramfs applies it before the root is
mounted. That makes the write power-fail safe: the staged image and its
record are only deleted after the write has been read back off the device
and hashed, so an interrupted install just happens again next boot, and a
write that keeps failing is abandoned after three attempts.

Single slot, not A/B. Two ~50MB slots do not fit in the Pico Mini's 128MB
NAND alongside userdata, and a design that only works on QEMU would have
to be thrown away for hardware.

Update format. UPDATE.ndsw is a zip of rootfs.squashfs (padded squashfs
with the dm-verity hash tree appended), manifest.json and manifest.sig.
The manifest carries the image sha256 and the verity parameters, so
signing the manifest covers the image. Two fields beyond the proposed
format: "platform" (qemu-aarch64 / luckfox-armv7), refused on a mismatch
because both images come out of this repo with the same filename and one
wrong copy onto real hardware is a reflash; and optional "min_kernel".

Signing is RSA-4096/SHA-256 verified by a dependency-free PKCS#1 v1.5
verifier (System/core/UpdateService/signing.py) -- real gnupg2 on the
device would have cost 4-6MB of libgcrypt/libassuan/libksba for the same
security. It rebuilds the whole expected encoded block and compares it
whole, so Bleichenbacher'06-style short-padding forgeries and SHA-1
algorithm substitution are both rejected (tested). Releases are signed
with `openssl dgst -sha256 -sign`; NEODCT_SIGN_KEY unset still builds a
package, just unsigned, which is the BAD SIGNATURE path on purpose.

dm-verity is enforced by default (neodct.verity=enforce; permissive and
off exist as escape hatches, and a failure under enforce drops to a
rescue shell rather than a reboot loop). Honest scope: the root hash
comes from installed.prop on the user partition, so this is integrity,
not authenticity -- it catches NAND bit-rot, partial writes and corrupt
flash on every block read, while authenticity comes from the signature
check the app does before staging. Anyone able to rewrite the user
partition can rewrite the system partition too. The upgrade is
CONFIG_DM_VERITY_VERIFY_ROOTHASH_SIG with the release cert built into the
kernel, which needs no userspace crypto at all.

Version metadata had to move. system.os.* lived in
/NeoDCT/User/settings.prop, which only appeared to work because an update
replaced the whole filesystem including that file. With /NeoDCT/User on
its own partition it survives an update, so the phone would have reported
its factory version forever. Those keys now come from a read-only
/NeoDCT/System/version.prop generated at build time from os-release
VERSION_ID; SettingsStorage layers defaults < settings.prop <
version.prop and drops stale system.os.* keys it finds.

Read-only fallout fixed: no more `mount -o remount,rw /` in either
inittab; crash log to /NeoDCT/User/logs; PYTHONPYCACHEPREFIX to
/NeoDCT/User/.pycache (without it a read-only root re-parses the whole UI
every boot); S45modem's cache off /etc; host-built __pycache__ pruned
from the image (host python 3.14 != target 3.13.11 anyway). Stock
wallpapers moved to /NeoDCT/System/wallpapers -- they are image content,
like System/tones. The shipped seed DBs and settings.prop were dropped:
init_databases() already creates schemas and DEFAULTS covers the rest, so
an empty user partition self-provisions.

First real boot found two initramfs bugs, both now covered by tests:

* No library search aliases. glibc's built-in path here is /lib64 and
  /usr/lib64, and an initramfs has no /etc/ld.so.cache to redirect it, so
  libraries in /lib were invisible and boot died at "/bin/sh: error while
  loading shared libraries: libresolv.so.2". The target tree solves this with
  lib64 -> lib symlinks; mkinitramfs now mirrors them (lib64, usr/lib,
  usr/lib64 all -> lib) so it does not matter which path the loader was built
  with, or which libc.
* Three applets used by the scripts (wc, tr, dirname) had no busybox symlink.
  That class of bug can be silent rather than loud: `wc` failing inside a
  command substitution yields an empty size, which reads as a truncated image
  and discards a perfectly good update. test_initramfs_applets.py now scans
  both scripts for command names and fails if APPLETS does not cover them, so
  the list cannot drift from the code again. Dropped findfs, which this
  busybox does not build and nothing calls.

Second real boot: the system image was never found. "no /sbin/init in the
system image" was the initramfs having mounted the SD card as root --
virtio-mmio devices are NOT enumerated in the order QEMU is handed them, so
neodct.sys=/dev/vda pointed at the wrong disk. (Confirmed by verity=off
failing identically, and by system.img starting with "hsqs" as it should.)

Device names from the cmdline are now a hint only. find_system_device()
identifies the system image by its squashfs magic ("hsqs", conveniently
printable, so no od needed) and find_user_device() by the NDUSER label, both
falling back to scanning every block device. Chosen devices are always
logged, since that is the first thing worth knowing when this goes wrong.
This is also more robust for real hardware, where the names differ again
(mmcblk, ubiblock).

blkid was the wrong question. try_mount now asks the kernel: it tries vfat,

"staged update is incomplete; discarding" was a real staged update being
thrown away, not a signature check. The record stores image=, and the app
writes it as /NeoDCT/User/.ndsys/pending.img -- correct where the app runs,
meaningless in the initramfs, which has the same partition mounted at
/mnt/user. The `[ ! -f "$image" ]` guard therefore always failed.

name that is only valid in one context (device order, loader search path,
mount namespace). Anything crossing the initramfs/system boundary should be
treated as needing re-resolution, not re-use.

Recovery entry points wired up: NEODCT_RECOVERY=1 (neodct.recovery=1 on the
cmdline) and a one-shot flag file, /NeoDCT/User/.ndsys/boot_recovery, which is

Recovery navigation: arrow keys echoed as ^[[A and the menu appeared frozen.
Raw mode was only applied to the primary tty, but in QEMU both the framebuffer
VT (tty1) and the serial console are live and there is no way to know which
one the user is typing into -- and without raw mode `dd bs=1 count=1` blocks
for a whole line, which an arrow key never completes.

Now every candidate tty gets raw -echo and the menu is drawn to all of them.
Digits also move the selection (Enter still selects), which works even if raw
mode fails entirely: "3<Enter>" reads identically in raw and line-buffered
modes, and unlike select-on-digit a stray Enter cannot pick something by
accident. j/k still work for terminals with no arrow keys.

Nine tests drive recovery_menu with scripted keys -- wrapping, digits,
out-of-range digits, digit-then-arrow. Writing them exposed read_key stashing
its value in a global for the digit case to read back; the menu now captures
the key once and cases on it.

Recovery input rewritten rather than patched again. The old version read one
tty and put only that one in raw mode, but in QEMU the framebuffer VT (tty1)
and the serial console are both live and there is no way to know which the
user is typing into -- so half the time arrows echoed as ^[[A and Enter did
nothing.

Now every candidate tty is put in raw mode and pumped by its own `cat` into a
single FIFO, which the menu reads as fd 8. The FIFO is opened O_RDWR so the
open cannot block and read_key never sees EOF. Typing works in either window.
Without mkfifo it degrades to reading the primary tty directly.

Three bugs surfaced while writing the tests for it:

* LF=$(printf '\n') is the empty string -- command substitution strips
  trailing newlines -- so the Enter-as-LF case could never match and Enter
  presses arriving as \n were silently swallowed. Now a literal newline.
* ESC O A (application cursor mode, which some emulators send) was not
  handled at all, only ESC [ A.
* mkfifo had no busybox symlink, so the merge would have silently fallen back
  to one tty. The applet scanner caught it, which is what it is for; kill was
  added alongside it.

Also: recovery_confirm still wrote its warning straight to $TTY, so on a
two-tty setup the question appeared on one screen and the yes/no on both, and
it carried a dead `for line in $1; do :; done`. It uses say() now. The rescue
shell stops the pumps before handing over and restarts them after, or they
would fight over every keystroke.

read_key is now driven from a byte stream in tests (a regular file on fd 8),
which also pins that the fd is opened once and read sequentially -- reopening
per call would restart at byte 0 and parse the same key forever.

initramfs: identify the system device by disk serial, and read recovery's
keys off the screen it draws on

Two faults, both of which made recovery unusable for the thing it exists to
do -- reinstalling a phone that cannot boot.

## The system device could not be found once it was wiped

find_system_device identified the system image by its squashfs magic, which
works right up until "wipe system" zeroes it -- exactly when knowing the
answer matters. The cmdline hint is no fallback: QEMU does not enumerate
virtio-mmio devices in the order they are given, so `system, user, card`
comes up in the guest as vda=card, vdb=user, vdc=system, and neodct.sys=
/dev/vda has always pointed at the wrong disk. Confirmed by reading
/sys/block/*/serial in a booted guest. With a wiped image and no serials the
initramfs picked /dev/vda and would have installed onto the SD card.

The drives now carry a disk serial (NDSYS / NDUSER / NDCARD, set with
-device virtio-blk-device,serial=), read back from /sys/block/*/serial. A
serial belongs to the device rather than to anything written on it, so
zeroing the image cannot take it away, and it outranks both the hint and the
content scan -- which also stops an SD card someone has written a system
image onto from being adopted as the root filesystem.

The scan and the hint stay as fallbacks: an eMMC partition has no disk
serial, and on real hardware the names are stable anyway, which is why this
was only ever a QEMU problem.

Verified in QEMU with the first megabyte of system.img zeroed: `system=
/dev/vdc` with serials, `system=/dev/vda` (the card) without.

## Arrow keys did nothing on the phone's screen

Two independent reasons, either of which was enough on its own.

The terminal would not stay in character-at-a-time mode. `stty -F /dev/tty1
raw -echo`, and equally `stty ... < /dev/tty1`, opens the terminal, sets the
mode and closes it -- and the VT console driver sets TTY_DRIVER_RESET_TERMIOS
(drivers/tty/vt/vt.c), so closing the last descriptor puts it straight back
to canonical with echo on. The mode was gone before anything read a byte,
which is why every arrow press printed ^[[B over the menu and nothing was
readable until Enter. recovery_input_start now holds the terminal open on fd
8 for as long as recovery runs and sets the mode through that descriptor.

And the keys were read from the shell's stdin, which for init is /dev/console
-- the serial port. The screen's VT was never read at all, so input "worked"
over serial and did nothing on the phone. read_key reads fd 8.

read_key is back to dd rather than `read -n 1`: this busybox is built without
CONFIG_ASH_READ_NCHARS, so ash's read has no -n and takes a whole line.

The pump-and-FIFO merge is gone with it. Reading both ttys needed two readers
merged into one stream, and it wedged in the guest -- the console pump sat in
pipe_lock in D state, blocking the shared FIFO for everything else. Recovery
now drives one terminal, drawn on and read from; neodct.rectty=/dev/console
moves the whole UI to the serial port, which is what a headless run wants.
That also fixes the menu being painted twice, once on the display and once in
the terminal QEMU was started from.

## Tests

Device identification is driven against a stand-in /sys/block and /dev,
including the wiped case and a squashfs planted on the card.

The input path is driven through a real pty, with a shim that gives it the
one property of a VT that matters here: a mode set through a descriptor
nobody holds is undone when the setting process exits. Without it the bug is
invisible on the host, because a pty keeps whatever it is told. The pty test
reproduced the exact symptom -- b'^[[B' echoed back, no key delivered.

Verified end to end in QEMU: arrows move the selection on the display, Enter
on "reboot" reboots, and nothing is painted on the serial console.

update: a software-update page worth reading, and pictures in .ndsw

The update app worked and looked like a debugging tool. Installing meant
paging through five screens of release notes at 20px, then answering four
questions -- install?, back up?, the backup's own "done" dialog, restart? --
each one a modal with a warning triangle on it, whether or not anything was
wrong. The progress bar, the one thing that already looked right, had "0.0 MB
of 0.0 MB" drawn straight through it.

It is now one page and one bar.

## The page

DetailPage (framework) is a page you read: a picture, a title, a couple of
lines of detail beside it, then body text, all in one column that scrolls a
line at a time with up/down and carries the Nokia scrollbar when there is
more below. The update page is a picture, the version, size and build date,
"Verified" or "Not signed", and the release notes -- softkey Install.

Three rules in it are worth knowing, because each one is a thing that looked
wrong before:

* The hero row shrinks until the body starts on the same screen. Picture and
  details stacked, they filled the screen on their own and everything worth
  reading was below the fold; beside each other they cost 72 pixels. If the
  details still do not fit, the picture gives ground rather than the text.
* A block that would be sliced by the bottom edge is left for the next
  scroll. Half a line of type at the fold reads as a rendering bug.
* A page that fits is centred. Three words pinned to the top of an otherwise
  black screen reads as a crash.

The same paragraph rule went into TextScroller, which every other app's help
text still uses: a blank line is a gap of a third of a line, not an empty
line of 20px type. Four short paragraphs used to need three screens.

## The bar

ProgressScreen (framework) keeps the bar and gives it room: step label above,
percentage and byte count below, hint at the foot, nothing on top of it. One
screen covers the whole install -- "Backing up data" then "Copying update"
via set_step, not two screens that flicker between them. It repaints only
when the whole percentage changes, so the copy loop can call it per 256KB
chunk without slowing the copy down. Labels and hints drop a font size, then
ellipsize, rather than running off both edges.

## The backup is not a question

It happens while the bar is on screen. User data is on its own partition and
an update does not touch it, so the backup is belt and braces -- which means
a full or write-protected card is no reason to refuse to install. It is best
effort, and a failure is admitted on the last page instead of interrupting.

## Signature warnings

Same warning either way, "OK" on both -- "Acknowledge" was a word from a
lawyer. Outside engineering mode that dialog is the end of it. In
engineering mode it is followed by "Install Anyway?", which C cancels. An
unsigned image is how you end up stuck on a phone that will not boot, and a
dead phone cannot be talked out of it afterwards.

INVALID UPDATE and WRONG UPDATE FOR THIS PHONE are unchanged and still have
no way past them.

## Pictures in packages

.ndsw can carry thumbnail.png, a square PNG the phone draws at 64x64. Its
sha256 goes in manifest.json, so the one signature over the manifest covers
the art as well; write_ndsw is the only place that knows about both, so the
bytes written and the bytes signed cannot disagree. Art with no hash recorded
is treated as absent, and art that does not match its hash is dropped in
favour of the app icon -- it is decoration, and the image's own sha256 is
what says whether an update is safe. There is a 256KB cap read from the zip
directory, so an oversized "thumbnail" is refused without being decompressed.

`make update` picks up neodct/release-thumbnail.png if it exists, or
NEODCT_UPDATE_THUMBNAIL=..., and mkupdate refuses anything that is not a PNG
or is over the cap rather than shipping art the phone will not draw.

## Tests

Three suites, all TDD'd, 82 tests:

* test_update_ui.py -- the widgets, judged on real drawn frames from the real
  font: no text within three pixels of the bar, nothing in the softkey bar,
  the notes start on the first screen, the bottom line is never cut in half.
* test_update_flow.py -- whole flows through the shipped app against a staged
  card with a real signed .ndsw on it. Installing is two key presses; the
  whole install is two screens and a bar (repaints are not screens); the
  release picture reaches the screen; the databases are on the card
  afterwards.
* test_systemupdate_app.py -- the policy, rewritten for the new flow: what is
  refused, what engineering mode may walk past, and that nothing asks about
  the backup.

tests/update_ui_fixtures.py stages the card, the release key and the version
file and hands back the real UI; NEODCT_UI_SHOTS=/some/dir writes every
screen the tests draw to PNG, which is how the design was reviewed.

Two harness fixes fell out of it: uistub's PathRemap now covers io.open (what
zipfile actually calls -- a package on the card was unreadable through the
stub) and shutil.copy2 (the backup), and test_sdcard_helper no longer leaves
its tmp path in Storage.MOUNT_POINT for the rest of the suite to trip over.

482 tests pass.

* **system.os.platform was a path on my machine.** Buildroot calls post-build
  scripts as `script TARGET_DIR $BR2_ROOTFS_POST_SCRIPT_ARGS

# t9: the keypad never told the apps it was a keypad

Everything T9 was already built. The engine, the on-disk dictionary, the
predictive widget, the mode indicator and both uinput bridges were finished and
green -- test_t9_engine 108 checks, test_t9_dict 587, test_widgets_text 2163 --
and none of it did anything on the phone. Pressing 2 in Phonebook typed "2".

Every one of those tests sets `ui.has_matrix_keypad` by hand, and that was the
whole bug: nothing ever set it for real inside an app.

## What was actually wrong

`nd_ui_init_app()` derived the flag the only way it could:

    ui->has_matrix_keypad = nd_input_has_matrix(ui->input);

An app's `ui->input` is the pipe the core hands it. A pipe has no matrix, by
construction, on every device -- so the flag was false in every app process
that has ever run, and nd_textinput.c:223, nd_textlong.c:526 and nd_t9ind.c:50
all hang off it. Every text field on the phone fell through to the QWERTY dev
path, and `nd_key_dev_char()` ends in a fall-through to `nd_key_digit_char()`,
so a keypad press typed its own digit and stopped there. No letters, no
multi-tap, no predictive, no # mode switching, and no mode indicator drawn.

It was written down. OPEN-QUESTIONS.md BR-3 found it while porting the browser
launcher and left it, because lib/nd_ui.c was not that work package's file:

  > That also means the T9 mode indicator is never drawn inside an app, which
  > is a separate bug in lib/nd_ui.c / lib/nd_input.c [...] Not fixed.

LinuxShell and the Browser had each grown the same workaround -- re-read
/NeoDCT/User/keymap.json and infer the hardware from it -- so the two uinput
bridges worked while the fourteen widgets did not.

## The fix

The core knows the answer, because it opened the backend. So it says so.
`nd_proc_launch_app()` sets NEODCT_KEYPAD_MATRIX=1 when its own keypad is the
matrix, and `nd_ui_init_app()` reads that instead of interrogating the pipe.
Not a descriptor, so it is documented in nd_app.h beside the four that are.

Both bridge gates lost their keymap.json half and ask `nd_app_keypad_is_matrix()`
instead. That is not just tidier: a keymap on disk is a *claim* about the
hardware, while the environment carries the backend the core actually opened.
If the matrix failed to open and the core fell back to evdev, the old code
would have bridged a uinput keyboard on top of a real one and doubled every
press. test_browser.c now pins that -- a keymap.json alone must NOT bridge.

Two things worth knowing about the shape of it:

**NEODCT_T9 is a second, separate switch.** Unset in production and in every
golden capture; "0" forces T9 off, anything else forces it on. It is the only
way to exercise multi-tap over a QWERTY keyboard, and it is deliberately not
folded into what the bridges ask, because the two are different questions:
`ui->has_matrix_keypad` is "should keys mean T9?", `nd_app_keypad_is_matrix()`
is "is the console's keyboard missing?". Forcing T9 on at a desk must not
bridge a second keyboard into netsurf.

**build_envp() had to start allocating.** It filled a `const char *[64]` and
silently stopped copying when it ran out. The phone's environment is small so
nobody had ever seen it, but an ordinary desktop shell exports ~66 entries and
the copy then lost whatever sat at the *end* of environ -- which is exactly
where setenv() puts a variable set just before a launch. NEODCT_T9 was the
first thing to notice, by not arriving. Sized from the real environment now, so
there is no cliff to fall off, and $HOME cannot go missing because it sorted
late.

## How it is proved

test/apps/T9App plus test/unit/test_t9_app.c, in the shape test_svc.c
established: a real app.so, dlopen()ed by the real nd-apprun, in a real child
forked by the real nd_proc_launch_app(), driving a real nd_textinput over real
keypad codes and reporting the string that came out. Four launches -- no
matrix, matrix, override on, override off.

It refuses to set the flag by hand, because that is what let this survive.

    no matrix    2,2,2,3 -> "2223"     the old behaviour, pinned so it
                                       cannot come back by accident
    matrix       2,2,2,3 -> "cd"       multi-tap
                 #,2,2,2 -> "C" ABC    mode switching, from inside the app
                 #,#,2,3 -> "23" 123
                 #,#,#,4,6,6,3 -> "home"

The last one opens the shipped /NeoDCT/System/core/t9.dict from inside the app
process, so it also proves the dictionary is reachable across the boundary.
"home" and not "good": t9.dict is ordered by digit key then by frequency.

45 checks. Everything else still passes, ASan included, and all 48 golden
frames are still byte-exact -- NEODCT_T9 is unset in uistub, nd-shoot and CI,
so T-5 holds and no reference capture moves.

musl-gcc is not installed on this host, so verify-c-build.sh check 3 skipped as
it always does here; check 3b (32-bit, unsigned char, -Wconversion) passes.

# modem: the info app could not tell "no modem" from "could not ask"

Reported as "it says simulation mode even on real hardware", then narrowed by
the owner to "modem works completely, just the info app doesn't".

## What is proven

The core-to-app path is correct, and that is now a test rather than an
opinion. test_svc.c grew a modem that ANSWERS -- a pty that replies OK, which
is all _probe_ports() and the init sequence need -- so nd_modem_has_hardware()
can be TRUE on a build host for the first time. Against it:

  * the loopback case asks twice over a live server and gets hardware=1 and
    the real port back both times;
  * SvcApp, a real app.so in a real child forked by the real
    nd_proc_launch_app(), reports status_hardware=1 and status_port over
    NEODCT_SERVICE_FD.

Every existing case ran against a modem in Simulation Mode, so
`CHECK_INT(st.hardware, direct.hardware)` was comparing false against false
and would have passed just as happily if the wire zeroed the field. It does
not zero it. 114 checks now, up from 95.

## What was actually wrong

**The app rendered a failed service call as "SIMULATION".** It threw away
nd_svc_modem_status()'s return value, and that return value is the difference
between "the core says there is no modem" and "the question never reached the
core". On failure the client hands back the documented "nothing is known"
snapshot -- hardware=0 -- so an unanswered call drew the phone's modem as
missing. Three states now, not two: the port, SIMULATION, or NO LINK TO CORE.

**And the probe never said why.** "HARDWARE NOT FOUND: Running in Simulation
Mode." was the whole output, on a phone with a modem visibly plugged into it.
probe_ports() dropped every errno and every refusal on the floor -- including
the one failure that is completely silent, nd_modem__acquire() losing the AT
port flock to S45modem's background redial. It now names the cause:

    No AT port: no candidate AT ports (no ttyUSB* in /sys/class/tty)
    No AT port: /dev/ttyUSB2: Permission denied
    No AT port: /dev/ttyUSB2: AT -> no reply
    No AT port: the AT port lock is held (S45modem or atcmd is mid-session)

Printed on CHANGE, not every time: the probe retries every 10 s forever while
there is no modem, and an unconditional print would put the same line on the
serial console six times a minute for the life of the phone.

nd_modem__open_port() now preserves errno across its own teardown, because
close() may set one of its own and the caller prints ours.

## And it says it on the phone

The reason rides the service wire (nd_modem_status.probe_why, appended, so no
existing field moves -- M-17) and the engineering Modem app draws it as a WHY
row beside PORTS. This app exists to be read on a device with no serial
console attached; the Python could print to a terminal the developer was
already watching, and this cannot.

455 checks in test_modem (up from 433), covering all four reasons and the
print-on-change rule -- a diagnostic nobody checked is a diagnostic that rots.

No golden frame moves: probe_why is empty in nd-shoot, so the WHY row does not
appear and all 48 stay byte-exact. That is a consequence, not a constraint --
per the owner, the OS is function-matched and the frames are not a spec.

## The reported symptom did not reproduce

Recorded plainly, because it changes what this commit is. The owner reopened
the app on an UNCHANGED system -- none of the above was flashed -- and found it
working: "it actually is working, and may have worked the whole time." So none
of this fixed what was reported, and nothing here should be read as having
done so.

The most likely explanation, and the reason the WHY row earns its place
anyway: the core re-probes every PROBE_RETRY_S while it has no modem
(nd_modem.c, the !m->hardware branch of poll()). Open the app inside that
window -- ttyUSB nodes not enumerated yet, or S45modem mid-dial holding the
flock -- and it says SIMULATION; open it later and it does not. An
intermittent readout with no stated cause is exactly the thing the probe used
to be silent about.

What is defended on its own merits, independent of the report:

  * open_port() discarded errno and probe_ports() dropped every rejection,
    including a lock loss that returned false in total silence;
  * the app drew a failed service call as a fact about the phone;
  * NO TEST IN THE TREE HAD EVER RUN WITH hardware == true, so the assertion
    that was supposed to cover this compared false against false.

Note for whoever reads a bug report about this next: the home screen cannot
rule Simulation Mode in or out. nd_layout.c:404 draws the element's sim_val
when signal_level() is -1, so a phone with no modem shows CONSTANT FAKE BARS.
Bars that move or vanish are the real ones.

bluetooth: the kernel is the whole stack, and an app that proves it

A TP-Link UB500 (2357:0604) now works on this phone, and there is an
engineering app -- Bluetooth, id 9007 -- whose job is to say which of the five
things that have to be true is not.

## No BlueZ, and that is the design

The obvious way to talk to a dongle is bluetoothd. BR2_PACKAGE_BLUEZ5_UTILS
selects dbus and libglib2, so "is there an adapter and what is its address"
would have cost a message bus, ~1.5 MB of object library and a resident
daemon, on a 64 MB device, for a feature that is engineering-only.

Everything this needs is a kernel ioctl on an AF_BLUETOOTH socket, served by
the kernel's own BlueZ core: HCIGETDEVLIST, HCIGETDEVINFO, HCIDEVUP,
HCIINQUIRY. So userspace is lib/nd_bt.c, about 400 lines, inside libneodct,
and nothing else exists. Measured cost of the kernel side: the uncompressed
Image went from 14,514,688 to 15,245,824 bytes, +714 KB of resident text.
bluetoothd plus its dependencies would have been several times that on top.

That argument stops holding the day pairing, A2DP or RFCOMM is wanted -- all
three need the event-driven HCI session bluetoothd exists to run. nd_bt.h
says so at the point where someone would go looking. It is also why an
inquiry reports addresses and device classes but no names or RSSI: the
inquiry ioctl carries neither, for the same reason.

## The structs are copied, and that is checked rather than asserted

struct hci_dev_info lives in include/net/bluetooth/hci_sock.h, which is not a
UAPI header -- nothing installs it, and the only userspace copy ships with
bluez-libs, which is the dependency this module exists to avoid. So they are
declared again in nd_bt.c, and every offset was checked against
linux-6.12.47's own declaration AND measured on the machine: sizeof 92, name
at 2, bdaddr at 10, flags at 16, type at 20, features at 21, pkt_type at 32.
Nothing in them is a pointer or a long, so 32-bit ARM and the x86-64 the
tests run on agree, which is what makes a host test meaningful at all.

The ioctl numbers are computed with _IOR/_IOW rather than pasted.

## ioctl's second argument has two types

musl declares `int ioctl(int, int, ...)`; glibc declares
`int ioctl(int, unsigned long, ...)`. Three of these requests have bit 31 set
because _IOR puts _IOC_READ there -- HCIGETDEVLIST is 0x800448D2 -- so there
is no single type for the constant that is silent under -Wconversion on both:
as unsigned it is a sign change on musl, as int it is a sign extension on
glibc. The phone is musl and the tests are glibc and both have to be right.

One wrapper per argument shape, one explicit cast selected on __GLIBC__. The
bits the kernel sees are identical either way; sys_ioctl takes the request as
unsigned int. Verified clean under host gcc, aarch64-buildroot-linux-musl-gcc
and arm-buildroot-linux-musleabihf-gcc.

## The BD_ADDR is stored backwards

It crosses the HCI wire least-significant byte first and the kernel hands it
over as it arrived, so the printed form is the reverse of the bytes.
nd_bt_addr_str() is the only place that reversal happens. Getting it the
wrong way round produces a plausible-looking address that no other tool
agrees with, so the test pins it against the real UB500's, which is checkable
twice over: hciconfig says B8:FB:B3:9D:0D:C7 and the dongle's own USB iSerial
is B8FBB39D0DC7.

## The self test is the point of the app

Bringing a dongle up fails in five places and four of them look identical
from outside. KERNEL is socket(AF_BLUETOOTH) -- CONFIG_BT is off, which on
this device means a reflash, since an .ndsw carries no kernel. ADAPTER is
HCIGETDEVLIST empty -- btusb did not bind. ADDRESS is BD_ADDR all zeros --
btrtl asked for rtl8761bu_fw.bin and did not get it, and this is the one that
looks most like working hardware because hci0 exists. RADIO is HCIDEVUP.
SCAN is the inquiry, the only step that proves the radio transmitted.

Each runs only if the one before it passed and the rest show "--" rather than
FAIL, because five failures caused by one unplugged dongle say less than one
failure and four dashes. RADIO reads the flags back after HCIDEVUP returns 0
rather than trusting it: a controller that fails its own init leaves HCI_UP
clear. Hearing nobody on SCAN is a pass -- the radio worked, the room was
empty -- and saying FAILED there would send a technician after a working
dongle.

## Two screens that block, and the frame goes out first

HCIINQUIRY does not return until the controller has finished listening --
5.12 s, no poll, no partial result. Both pages commit their "Scanning..."
frame BEFORE the ioctl; drawing it after leaves the previous screen up for
five seconds and the phone looks hung. The wait is interruptible (the kernel
waits on the HCI_INQUIRY bit with TASK_INTERRUPTIBLE and nd-apprun installs
SIGTERM without SA_RESTART), so an incoming call arrives as EINTR and
app_shutdown() still runs on time. That is what makes a five-second blocking
ioctl acceptable inside the teardown contract at all.

## Layout, measured rather than guessed

An address is 157 px in font_s. So the scan list puts it at x=8 and the class
name at x=168, where FuelGauge's pages keep the 8/70 split -- a two-column
address at x=70 would put its last octet past the right edge. A long class
name is clipped by the canvas and that is fine; clipping the address would
not be. The row struct's fields are `left`/`right` and not `label`/`value`
for the same reason: on one of the three pages they are the other way round.

"UP RUNNING PSCAN ISCAN" is 217 px against a 170 px column, so PSCAN and
ISCAN get their own row. That is not only a layout dodge: page scan and
inquiry scan answer "can something else find this phone" and the other flags
answer "is the radio alive", which are the two questions a bring-up screen is
for.

bt: pairing needs an agent, and there never was one

Pairing earbuds has never once produced a bond. It looked like it had --
the phone said "Connected", BlueZ stored a device record, and audio routing
switched over -- but the record it wrote tells the real story:

    [General]
    Name=Smokin' Buds
    Class=0x240404
    Trusted=true
    Services=...0000110b... (A2DP browsed fine)

Name, class, and a full service list, so a connection plainly happened. No
[LinkKey] section, so it was never authenticated. `bluetoothctl info` agrees:
Paired: no, Bonded: no. There was nothing to reconnect to, which is why the
next attempt failed in under a second instead of timing out.

BlueZ will not complete Secure Simple Pairing unless some agent is registered
to answer for the local side; with none it cancels the exchange outright. A
one-shot `bluetoothctl pair XX` registers no agent unless asked, and we never
asked. The peer sees the attempt abandoned and goes back to advertising --
heard from the earbuds as "ready to pair" a second time.

That second announcement was blamed on --timeout in an earlier commit here,
on the theory that bluetoothctl was exiting before the handshake finished.
Removing it did change the outcome, so it looked confirmed, and it was the
wrong cause: what actually got through was an UNAUTHENTICATED connect while
the earbuds happened to be sitting in open pairing mode. The bond was missing
the whole time. --timeout stays off pair and connect regardless; that part of
the reasoning still holds for its own reasons.

cmd_build now passes --agent NoInputNoOutput for pair and connect. That is
the honest capability for a phone with no keypad to type a passkey on and no
display to show one, and it is also the useful one: it selects the "Just
Works" association model, which BlueZ auto-confirms for a pairing we
initiated. The agent has to exist. It never has to be asked anything.

Query verbs do not get one. An agent registration is a D-Bus round trip and
a default-agent claim, and taking it out on every `devices` poll would be
noise -- claiming the default agent while a pairing is in flight is worse
than noise.

Four tests in test_btaudio.c: pair and connect carry the agent, the query
verbs stay clean, and everything at once still fits argv with room for the
NULL (worst case is exactly eight slots, which is what ND_BTAUDIO_ARGV_MAX
allows). 75 checks in that file, suite green.

Not yet done: nothing watches for the earbuds disconnecting on their own.
Powering them off leaves ALSA pointed at a bluealsa PCM that no longer has a
transport. Settings' Disconnect row reverts the route correctly; a core
service that notices it happening anywhere else is still owed.

bt: audio goes the other way, and daemons kept the core's pipe

Two bugs, one symptom each, found by finally getting a real error message out
of the phone instead of reasoning about the code.

## a2dp-source, not a2dp-sink

bluealsa's -p names the profile THIS device implements, not the peer's.
Earbuds are an A2DP Sink; for the phone to send them music it must register
as an A2DP Source. It registered a2dp-sink, offering the phone as a speaker,
so a connection to earbuds found no complementary profile at either end:

    Failed to connect: org.bluez.Error.Failed br-connection-profile-unavailable

That error names no profile, and it arrives at exactly the moment pairing
would, so it reads as a pairing failure. It is not one. The comment that was
there had the physics right -- "this phone is the SOURCE of the music and the
earbuds are the sink" -- and then passed the flag for the opposite.

With this the Skullcandy buds connect, announce it themselves, and play an
mp3 off the SD card.

## daemons must not inherit the core's descriptors

Leaving Settings froze the whole UI, but only after Bluetooth had been used.
From the running phone:

    nd-core    fd 9  -> pipe:[277]   (read end, blocked in pipe_read)
    bluealsa   fd 10 -> pipe:[277]   (write end)
    bluetoothd fd 10 -> pipe:[277]   (write end)

spawn_quiet() points the daemons' stdout and stderr at /dev/null, which looks
sufficient. execve keeps every OTHER inherited descriptor, and the app had
inherited the pipe nd-core reads it through. Settings exits, its own copy
goes, and the pipe still does not reach EOF, because two daemons that are
SUPPOSED to outlive it are holding the write end. The core waits forever.

nd_proc_spec gains close_others: close everything above stderr in the child,
after the fds[] mappings are installed and before the execve. Off by default,
because an app is meant to inherit what the core hands it -- the crash pipe
and the service socket are passed exactly that way. bluetoothd, bluealsa and
dbus-daemon opt in.

sysconf() is called before the fork, not in the child: it is not on the
async-signal-safe list. fds 0-2 are left alone, because closing stdin frees
the number for the next open() in the child to claim, and a daemon writing
into what it believes is a file and is actually descriptor 0 is a worse bug
than this one.

test_proc.c reproduces the symptom rather than the mechanism: spawn a
long-lived child, close our own write end, read non-blocking. EAGAIN means
something still holds it, 0 means nothing does. Blocking would reproduce the
freeze faithfully and prove nothing. RED was "got -1 want 0".

## Corrections to the two commits above this one

The earlier claim that --timeout was cutting pairing short was wrong. It was
never the cause; what got through once was an UNAUTHENTICATED connect while
the earbuds sat in open pairing mode, and the device record BlueZ wrote had
no [LinkKey] section to show for it. The missing agent (previous commit) was
real but not sufficient, and the profile being backwards is what actually
blocked every connection.

Still owed: nothing watches for the earbuds disconnecting on their own, so
powering them off leaves ALSA pointed at a bluealsa PCM with no transport
behind it. Settings' Disconnect row reverts the route correctly; a core
service that notices it happening anywhere else is not written yet.

update: the phone's system partition cannot be written with dd

Updates have never once installed on real hardware. They download, the phone
reboots, and nothing has changed. Three separate bugs, each of which alone is
enough to produce exactly that, and none of which any test could see.

## 1. dd cannot write the system partition

The Luckfox cmdline hands the initramfs

    ubi.mtd=4 ubi.block=0,system neodct.sys=/dev/ubiblock0_0

and ubiblock is READ-ONLY. The kernel registers that disk read-only on
purpose: it exists so squashfs and dm-verity have a block device to READ.
`dd of=/dev/ubiblock0_0` therefore fails for everyone, always -- and
apply_pending's error path turns that into silence:

    elif ! dd if="$image" of="$SYS_DEV" ...; then
        log "write to $SYS_DEV failed; retrying on the next boot"
        return 0

It logs, returns, boots the old system, and after three attempts discards the
update. The owner sees a reboot.

Writing a UBI volume goes through its character device, and a STATIC volume
cannot be seek-and-written at all: an update is a transaction opened with the
final size. That is ubiupdatevol's whole job, and why no ordinary tool
substitutes. ubi_volume_for() maps /dev/ubiblock0_0 to /dev/ubi0_0 and
write_system() picks the writer, keeping the no-copy streaming design --
busybox's ubiupdatevol takes "-" as stdin with -s SIZE.

## 2. the read-back hashed a device nothing had invalidated

The check after writing hashed $SYS_DEV, the ubiblock disk. The kernel's only
reaction to a static volume being updated is ubiblock_resize()
(drivers/mtd/ubi/block.c, UBI_VOLUME_UPDATED), so when a new image happens to
be the same size as the old one there is no capacity change and no reason for
the block device to drop its cached pages. The read-back would then hash the
PREVIOUS system and reject a write that was perfectly good. It now reads back
through the node it wrote.

## 3. the volume is exactly as big as the image that was flashed

mknand.sh gives the system volume no size, so ubinize "assume[s] minimum to
fit image". A static volume cannot take a larger one, and NeoDCT images grow:
0.4.4a added 2.7 MB when Bluetooth arrived. Fixing only #1 would have bought
one working update and then failed again on the next release that grew.

ubi_fit() reads the real capacity out of sysfs (reserved_ebs * usable_eb_size)
and grows the volume with ubirsvol only when it has to -- a resize rewrites
the volume table, which is not worth doing on every update that already fits.
There is room: 100 MB partition, sub-50 MB image.

## why none of this was caught

test_initramfs_apply.py drives the applier with ordinary files standing in for
the partition, and dd is perfectly happy writing a file. QEMU's system device
is /dev/vda, which is genuinely writable. The QEMU kernel had NO MTD or UBI at
all, so nothing on this side could exercise the phone's storage even in
principle. Every test was true and none of them were about the phone.

That is fixed structurally, not just for these three bugs: the QEMU kernel now
builds CONFIG_MTD_UBI and UBI_BLOCK, with mtdram as a MODULE so it costs
nothing on an ordinary boot, and neodct/tools/test_update_ubi.sh attaches a
real UBI device, creates a real static volume, and drives the real applier at
it. Both cases are covered -- an image that fits, and one that does not and
has to grow the volume. Scenario B failed before the fix and passes after.

neodct/tools/test_update_e2e.sh is the other half: a real signed package on a
real card, staged into the real state directory, applied by the real initramfs
across a real reboot, with VERSION_ID read back off the running system.
Proven 0.4.4a -> 0.4.3a. It also caught the applier retrying correctly after
the harness killed QEMU mid-write, which was not planned and is the crash
safety working.

## the applets have to be in the INITRAMFS

ubiupdatevol and ubirsvol are added to mkinitramfs.APPLETS and enabled in the
busybox fragment; CONFIG_UBIUPDATEVOL was explicitly "not set", so the tool did
not exist at all. Both are named by tests directly, because ndsys-apply.sh
calls them through $NDSYS_UBIUPDATEVOL / $NDSYS_UBIRSVOL and the scanner in
test_initramfs_applets.py can only see literal command names.

ubirsvol was very nearly missed: test_update_ubi.sh sources the applier on a
RUNNING phone, where every applet the target build installed is on the PATH,
while apply_pending really runs one step earlier in the initramfs, which has
only what mkinitramfs symlinks. It would have passed the test and failed on
the phone -- the same shape as the bug being fixed.

## delivery

CONFIG_INITRAMFS_SOURCE in the SDK kernel defconfig named the COPY of this
repo on the external drive rather than this one. The kernel embedded whatever
initramfs that tree last produced, so a fix to the applier could be committed,
tested and released here and still never reach the phone. Repointed, with the
previous defconfig kept beside it.

audio: S17audio never turned the capture path on

Hardening, NOT a fix for the bug it was written chasing. Read the last
section before believing otherwise.

S17audio has always done the routing -- find the USB card by usbid, write
asound.conf, bypass dmix -- and then stopped. It never touched the mixer, and
nothing else does either: there is no alsactl in this image, so no saved
state is restored at boot. The phone gets whatever the driver defaults to, on
every boot and every replug. That is a real gap whatever else is true.

enable_capture() now switches on anything named "... Capture Switch" and
raises anything named "... Capture Volume" to NEODCT_CAPTURE_LEVEL (80%).

## by numid, and only where the name is unambiguous

The obvious version is `amixer sset Mic 80%`, and on the hardware this was
written for it is WRONG. A real C-Media adapter (0d8c:0014), read off the
device itself, publishes:

    Mic Capture Volume      Mic Capture Switch
    Mic Playback Volume     Mic Playback Switch    <- monitor, mic to speaker
    Auto Gain Control       Speaker Playback Volume/Switch

ALSA's simple mixer merges the two Mic rows into ONE control carrying both
pvolume and cvolume, so sset raises the monitor path as well and puts the
microphone into the earpiece. On a phone that is feedback -- a worse bug than
the silence being chased. The first version of this commit did exactly that
and its own test passed, because the fake amixer in that test had no control
with both capabilities. The test now models the real card's control list.

Kernel control names have no such ambiguity, and numid avoids quoting a name
with spaces in it. A volume whose name does not say Capture is left alone:
snd-dummy publishes "Mic Volume" + "Mic Capture Switch", an old ISA-style
mixer where one volume serves both directions, and on the cards that matter
that shape is the monitor path. Switch on, volume untouched, deliberately.

Auto Gain Control is left alone too. It is a sound-quality choice rather than
a correctness one and not this script's decision to make.

## tests

Seven in test_s17audio.py against the real card's control layout, including
explicit ones that the monitor path, the speaker and AGC are NOT touched.
The script gained NEODCT_ASOUND_CONF / NEODCT_PROC_ASOUND / NEODCT_AMIXER
overrides so the whole thing can be driven, routing included -- it had no
tests at all before.

neodct/tools/test_mic_capture.sh does it against real ALSA: snd-dummy (a
module, so it costs nothing on an ordinary boot) gives a card with genuine
capture controls, it is muted first, and the real script with the real amixer
turns it back on. The unit tests use an amixer this commit wrote, so they
would pass just as happily if the parsing were wrong; this one would not.

## what this does NOT fix

The bug that prompted it: an electret on a C-Media card recording nothing on
the phone. Measured over the serial console on the hardware itself, capture
was already ON -- switch on, AGC on, volume 20 of 35 -- so this changes
nothing there. Raised to maximum, the capsule gives peak 27 and mean 12 out
of 32767, which is the noise floor. arecord runs clean at the right rate and
returns real data; there is simply no signal in it. The one promising number,
a peak of 8308, was the open-the-device transient and vanished on the next
recording.

The card, the driver, the mixer and MicTest are all behaving correctly. That
leaves the capsule or its wiring.

Also worth its own change, not made here: MicTest cannot tell those apart. It
sends arecord's stderr to /dev/null and treats an empty pipe as normal, so a
recorder that failed to open the device and a microphone recording silence
draw the identical flat line. For an app whose whole purpose is answering "is
the microphone working", that is the wrong answer to give twice.

modem: a call's uplink went to the codec with nothing attached to it

Calls played the far end's voice perfectly and sent silence back, with no
error anywhere. Both halves worked exactly as written; they were written for
a machine this phone is not.

Downlink uses ALSA's "default", which S17audio points at the USB sound card.
Uplink did not: it scanned /proc/asound and took the first card carrying a
pcm*c node, byte-sorted. The comment above it explains why -- on QEMU
"default" is a playback-only USB Audio device that arecord cannot open, so
the scan exists to route around it.

On QEMU that scan lands on the microphone by luck: card 0 has no capture node
at all, so the first match is the real one. On the phone card 0 is the
RV1103's own rv-acodec. It HAS a capture node, arecord opens it without
complaint, and on this board it is connected to nothing. So the two ends of a
call ran on two different cards, and the one with the microphone on it was
not the one being recorded.

The fix is the test S17audio already uses for the playback card: a USB sound
card announces itself with a usbid and an on-chip codec does not. Prefer a
USB card that can capture, fall back to the first card that can capture at
all. Both ends of a call now land on the same hardware by construction rather
than by luck, and a board that grows a wired-up on-chip microphone still
works.

Three tests, RED first at "got plughw:0,0 want plughw:1,0": the phone's
layout, QEMU's playback-only USB card (which must still be skipped), and the
no-USB fallback.

Found from the hardware, not from the code: the phone's own /proc/asound
listed capture nodes on both card0 and card1, which is the fact the QEMU
comment could not have known.
