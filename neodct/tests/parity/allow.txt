# allow.txt -- every way the emulator and the phone are allowed to differ,
# with the argument for each one.
#
# ============ READ THIS BEFORE YOU BELIEVE A LINE OF IT ============
#
# NO CAPTURE HAS EVER BEEN TAKEN FROM A LUCKFOX PICO MINI B. Nobody working on
# this branch has one. luckfox-armv7.inventory does not exist, so
# test_parity_allowlist.py runs SINGLE-SIDED and says so on every run:
# 0 of N records are verified against hardware. Every `hw` value below is a
# CLAIM, and every record says which it is in its own hw_evidence field rather
# than leaving it to the reader to notice.
#
# THE EMULATOR SIDE IS MEASURED, AND IT IS NOT MEASURED FROM AN IMAGE.
# qemu-armv7-probe.inventory was captured by parity_capture_probe.sh: the
# repo's own kernel (board/qemu/armv7-virt/linux.config), the exact machine
# run_qemu.sh assembles (-M virt -cpu cortex-a7 -smp 1 -m 64,
# force-legacy=false, mtdram.total_size=0 plus the Pico Mini's nandsim ID
# bytes and nandsim.parts=2,2,4,128,64, video=vfb:on), and a BUSYBOX INITRAMFS
# where the NeoDCT rootfs would be, because buildroot/output does not exist and
# a full build is hours. Two boots produced byte-identical files.
#
# The capture is taken WITH THE DEVICE TREE run_qemu.sh builds. That is not a
# detail: three of the records below turn on the difference between a
# subsystem being compiled in and a device being present, and a capture taken
# without -dtb would be of a machine nobody boots. parity_capture_probe.sh
# refuses to run if it cannot build the tree, where run_qemu.sh only warns --
# a session with no backlight is still worth having, a BASELINE with no
# backlight is not.
#
# So the emulator column is a real measurement of a real armv7 machine and it
# is NOT a measurement of a NeoDCT image. Everything below the image -- the
# kernel identity, MemTotal, the class trees, the MTD geometry, /proc, the
# input devices, the /dev families, the framebuffer ioctls -- is measured.
# Everything about the image -- os-release, /NeoDCT/platform, the users table,
# the mount set, and the six records that need libneodct -- reads ABSENT or
# UNAVAILABLE(nolib) and is a property of that initramfs. Those records carry
# the verdict `until-image` and MUST be revisited the first time
# parity_capture_qemu.sh runs on a built image. Calling any of them permanent
# would be this harness lying about its own evidence.
#
# ============ THE FOUR VERDICTS ============
#
#   until-stage-N   a divergence a named stage will close. This is what makes
#                   the file SHRINK, and it has now happened once. FIVE
#                   records said until-stage-5. Two of them -- cpufreq.cpu0
#                   and cpufreq.policies -- had nothing left to annotate once
#                   a device tree gave the emulator a policy, and were
#                   DELETED. Three -- class.backlight, class.power_supply and
#                   class.thermal -- still name a real difference, but not the
#                   one they used to: the emulator side is now what it is
#                   going to stay, so they are permanent with the argument
#                   rewritten. Zero until-stage-5 records remain, which
#                   test_the_surfaces_stage_closed_its_records asserts, and a
#                   record that had survived its own stage would have failed
#                   test_the_qemu_column_matches_the_committed_capture anyway,
#                   because the emulator column stops matching the capture.
#   until-image     the emulator side of this record is a property of the
#                   probe initramfs, not of the emulator. Settled by the first
#                   capture from a built image, not by any stage.
#   permanent       with an argument. uname.release is the honest example.
#   must-differ     REQUIRED to differ. If these ever agree the two images are
#                   indistinguishable, which is the exact failure D1 exists to
#                   prevent. parity_diff.py's check_must_differ() evaluates
#                   this verdict against the two CAPTURES rather than against
#                   the diff, because a diff only holds keys that differ -- so
#                   for as long as it was evaluated against the diff, a
#                   must-differ record whose two sides had come to agree was
#                   reported as STALE and the operator was told to delete it.
#
# ============ AND NO COLUMN MAY BE A TOTAL WILDCARD ============
#
# Eight of these records used to carry `hw ~.*` or `hw ~.+`, six of them
# permanent. The emulator column was pinned and the phone column matched any
# value the phone could ever report, so those records could only ever say "the
# emulator is what it was" and never "the two machines still agree" -- half an
# annotation, with the missing half being the one the file is named after.
# class.gpio was the sharpest: its own argument says what it exists to pin is
# `export` and `unexport`, and `~.*` pinned neither on the phone.
#
# So there are none now, and test_no_column_is_a_total_wildcard pins the count
# at zero. Where the phone's exact value cannot be predicted from this
# repository the SHAPE still can -- a listing rather than ABSENT, a mount
# record rather than a missing one -- and that is what each hw column says.
# Moving that count off zero means arguing in a diff that a divergence nobody
# can describe is still a described divergence.
#
# Fields: key / qemu / hw / verdict / hw_evidence / why. A value may be given
# as ~<regex> where it is genuinely a free variable; a BARE `~` is refused,
# because it used to mean a total wildcard in one code path and the empty
# regex in every other. One segment of `key` may be [*]. Continuation lines
# are indented.

key          class.gpio
qemu         [export gpiochip0 gpiochip512 unexport]
hw           ~\[export( gpiochip[0-9]+)+ unexport\]
verdict      permanent
hw_evidence  unmeasured-claim
why          The one surface here that is a STAND-IN rather than a copy, and
             it is recorded so that nobody mistakes it for the phone's. -M
             virt's only real controller is a pl061 with EIGHT lines at base
             512, so none of the pin numbers this tree hard-codes exists on it
             -- measured, `echo 53 > export` answers "export_store: invalid
             GPIO 53". gpiochip0 is CONFIG_GPIO_MOCKUP at
             gpio-mockup.gpio_mockup_ranges=0,64, which puts gpio53, gpio56
             and gpio57 -- ND_BL_GPIO_PIN and the panel's RST and DC -- where
             nd_backlight.c, S90display and neodctDisplay.c expect them. The
             phone's chips are the RV1103's own and will never match this
             listing. What the record really pins is `export` and `unexport`:
             they are the whole legacy sysfs GPIO interface, GPIO_SYSFS is
             `bool ... if EXPERT` with no default, and losing it is one
             olddefconfig away and silent. gpio-sim is what 6.12 recommends
             instead and cannot be used -- it is configfs-driven with no fixed
             gpiobase, so it cannot produce gpio53. That gpio-mockup is marked
             DEPRECATED is a recorded risk and not a reason to ship pin
             numbers that do not match the phone. AND THE hw COLUMN NOW PINS
             WHAT THE SENTENCE ABOVE SAYS THIS RECORD PINS. It was `~.*`, so
             the record asserted export and unexport on the emulator side and
             nothing whatever on the phone's -- half an annotation, and the
             sharpest case of it in this file, because a phone that lost
             GPIO_SYSFS would have been absorbed in silence and
             nd_backlight.c's GPIO tier writes into nothing without it. The
             listing is sorted byte-wise and e < g < u, so `export` is always
             first and `unexport` always last with the chips between:
             `~\[export( gpiochip[0-9]+)+ unexport\]` asserts both files on
             BOTH machines and leaves free only the chip names, which are the
             half that genuinely cannot match.

verdict      permanent
hw_evidence  unmeasured-claim
why          The one framebuffer field the two kernels set INDEPENDENTLY, and
             the only fb0 record force_mode() cannot move. The other ten now
             AGREE by construction: neodct_displayd runs on both machines and
             its FBIOPUT_VSCREENINFO puts vfb into 240x175x32 on each, so
             xres, yres, both virtuals, bits_per_pixel, line_length, visual
             and the three channel offsets are the phone's numbers here
             because the phone's own code put them here. This one is fixed at
             probe from vfb's compile-time VIDEOMEMSIZE
             (drivers/video/fbdev/vfb.c, 1 MB) and no ioctl can change it.
             .

             column is a shape rather than a number. vfb_check_var() refuses a
             mode whose line_length * yres_virtual exceeds videomemorysize, so
             a phone whose vfb is smaller than 168,000 bytes cannot be granted
             240x175x32 AT ALL: force_mode() falls back to 16 bpp, fb_bytespp
             becomes 2, convert_rect() takes its other branch, and the phone
             runs a different pixel pipeline from the emulator with nothing
             anywhere saying so. A value that is not 1048576 is not a fault as
             long as it clears 168,000; a value below it is the whole panel.
             The RV1103 SDK's 5.10 config is not in this repository
             (DECISIONS D6), so the phone's value is a claim -- but the
             daemon logs the depth it was granted on every start, and the
             first hardware boot settles it in one line of the log.
             .
             THE COLUMN ENCODES THE FLOOR RATHER THAN A DIGIT COUNT, and the
             first version of it did not: `~1?[0-9]{6,}` was six-or-more
             digits, so it MATCHED 131072 -- a 128 KiB vfb, which is below
             168,000 and is therefore exactly the phone this record exists to
             catch, reported as fine. The regex now admits 170,000 and up and
             refuses 167,999 and down, which is what the paragraph above says.
             It is one digit loose at the bottom (168,000 to 169,999 are
             refused) and that is deliberate: a bound a reader can check
             against the prose beats one that is exact and unreadable, and
             nothing can legitimately land in a 2 KB window above the floor.

             as a VALUE. `nandsim.parts=` is given five sizes and not six so
             that the chip's bad-block slack falls into the last partition
             rather than becoming an mtd6 the phone has no name for -- the
             full argument is three records above -- and mtd5 is therefore
             108,003,328 bytes here against the phone's 100 MiB. In 512-byte
             sectors, which is the unit /sys/block/*/size uses: 210,944
             against 204,800.
             .
             WITHOUT THIS RECORD IT WOULD HAVE BEEN THE ONE UNEXPLAINED
             DIFFERENCE IN THE FIRST HARDWARE DIFF, because the mtd.byname
             family is keyed by partition NAME and is `hw ABSENT` on both
             sides of that argument, while block.* is keyed by NODE name and
             mtdblock5 exists on both machines. The reasoning was written down
             and attached to the wrong key family.
             .
             AND ITS FOUR SIBLINGS AGREE, which is the good half of the same
             change: block.mtdblock0 through block.mtdblock4 are 512, 512,
             1024, 32768 and 16384 sectors -- PARTITIONS.md's 256 KiB env,
             256 KiB idblock, 512 KiB uboot, 16 MiB boot and 8 MiB userdata,
             exactly -- so five keys that used to be one 128 MB partition now
             match the phone by construction and are deliberately NOT listed
             here. `class.block` still differs and is deliberately not listed
             either: the emulator's listing carries vda and vdb, which are
             QEMU's transport for the images and have no phone analogue, and
             the phone's carries a ubiblock this probe has no UBI to make.
             That divergence predates this stage, it is about the IMAGE rather
             than the machine, and writing an hw column for it today would be
             inventing the phone's block listing -- which is the one thing
             mtd.byname.[*].erasesize refuses to do two records up.

key          dev.[*]
qemu         ~.*uid=0\(\?\) gid=0\(\?\)
hw           ~.*uid=[0-9]+\([a-z]+\) gid=[0-9]+\([a-z]+\)
verdict      until-image
hw_evidence  unmeasured-claim
why          Every owner in the probe capture reads (?) because the busybox
             initramfs has no /etc/passwd and no /etc/group to resolve against
             -- a fact about that rootfs, not about the emulator. The names
             are read from those two files directly and NOT through
             getpwuid(3), which is a correction the first probe boot forced:
             a statically cross-compiled glibc needs libnss_files.so.2 at
             runtime and returns NULL without it, so the same machine read by
             two builds of the same tool gave two answers. That is a READER
             difference, and reporting one of those as a machine difference is
             the exact failure this harness exists to avoid. Reading the files
             also means the names recorded here are the names
             nd_priv_lookup() would find.

key          mount.[*]
qemu         ~fstype=(rootfs|proc|sysfs|devtmpfs|devpts).*
hw           ~fstype=.+ options=.*
verdict      until-image
hw_evidence  unmeasured-claim
why          The probe initramfs mounts five things; a phone mounts a
             verity-covered squashfs root, /NeoDCT/System and the ext4
             /NeoDCT/User. Nothing INSIDE /NeoDCT/User is ever recorded -- it
             is the only writable partition and it holds the phonebook, the
             SMS databases and Remote Shell's private key -- so the mount
             point is the whole of what this harness says about it. Note also
             what is NOT masked in an option list: ro, rw, nosuid, nodev,
             noexec and relatime are exactly the options nd-selftest's mount
             section fails on, and a mask over them would hide the divergence
             this file exists to find. Only size=, nr_inodes= and blksize=
             are masked, because those are MemTotal/2 restated. This is also
             the one record here that exempts a SUBTREE and had a free hw
             column, which is the combination that lets one block cover
             everything under a prefix. `~fstype=.+ options=.*` keeps it an
             annotation: the phone side has to BE a mount record, so a mount
             point the emulator has and the phone does not reads ABSENT, fails
             to match, and stays unexplained -- which is the case worth
             hearing about.
             .
             WHAT IT STILL ABSORBS, written down rather than hidden: a
             difference in the OPTIONS on a point both machines have. Measured
             with a synthetic phone capture, /proc carrying nosuid,nodev,noexec
             on one side only is explained by this record. That is the exact
             class the paragraph above says a mask must never hide, and the
             reason it is tolerated here and nowhere else is that this record
             is until-image: the probe initramfs mounts five things and a
             phone mounts a verity root, /NeoDCT/System and an ext4
             /NeoDCT/User, so until there is a capture from a real image there
             is no honest option string to pin. THE FIRST CAPTURE FROM A BUILT
             IMAGE MUST SPLIT THIS RECORD: one per point, with the options on
             both sides. nd-selftest is the gate that fails on those options
             on the phone tonight; this one is only supposed to fail in a pull
             request next week, and today it cannot.
